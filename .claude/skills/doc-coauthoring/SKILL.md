# Doc Co-Authoring Workflow

三階段協作文件起草工作流。適合使用者有想法但還沒有清晰結構時使用。

## 觸發條件

- 使用者說「幫我寫一份…」「起草一個…」「我們來討論…文件」
- 提到 PRD、設計文件、決策文件、RFC、規格書、提案
- 看起來要開始一個需要多個章節的文件任務

**觸發後先問：** 要用三階段引導流程，還是直接自由起草？
如果使用者選自由起草，直接協助；如果接受引導，進入 Stage 1。

---

## Stage 1：脈絡蒐集

**目標：** 縮小「使用者知道的」與「agent 知道的」之間的落差。

詢問：
1. 這是什麼類型的文件？（結合 docs-governance skill 的 doc_type 清單）
2. 主要讀者是誰？（人類、AI Agent、還是兩者？）
3. 讀完這份文件，讀者應該能做什麼決定或行動？
4. 有沒有需要依循的模板或格式？（提示：參考 docs-governance skill）
5. 有什麼限制或背景脈絡要知道？

收到初始答案後，請使用者把所有相關脈絡都倒出來，再根據空白處追問 5–10 個問題。
直到充分理解邊界情況與取捨後才離開這個階段。

---

## Stage 2：精煉與結構

**目標：** 逐節建立文件，透過腦力激盪與反覆精煉達到高品質。

每個章節的流程：
1. 針對該節內容追問 5–10 個問題
2. 腦力激盪 5–20 個選項
3. 使用者決定保留／刪除／合併哪些
4. 起草該節
5. 只做外科手術式修改（`str_replace`），絕對不重印整份文件

從「最多未知數的章節」開始，摘要類章節留到最後。
連續 3 次迭代無實質改變後，問：「是否有哪些內容可以刪除而不損失重要資訊？」

---

## Stage 3：讀者測試

**目標：** 用一個沒有背景脈絡的 agent 測試文件是否自帶足夠資訊。

**有 subagent（Claude Code）：**
1. 預測讀者會問的 5–10 個問題
2. 用只拿到文件內容的 subagent 測試每個問題
3. 報告哪些答對了、哪些偏差或遺漏
4. 修正空白，回到 Stage 2 處理有問題的章節

**沒有 subagent（claude.ai web）：**
1. 預測 5–10 個讀者問題
2. 請使用者開一個新對話貼入文件測試
3. 蒐集回饋，修正

**結束條件：** 讀者 agent 能一致回答問題，沒有新的空白浮現。

---

## 完成後 → docs-governance

文件主體完成後，套用 docs-governance skill 完成：
- 判斷正確的 `doc_type` 與目錄位置
- 填寫完整的 frontmatter（`doc_id`、`bounded_context`、`status: draft` 等）
- 確認命名規則與 `title` 引號規則

---

## 原則

- 每次只問一個問題，不要一次轟炸
- 優先用選擇題而非開放式問題
- 所有編輯用 `str_replace`，絕對不重印整份文件
- 品質優先於速度
- 使用者可以隨時跳過或調整流程
