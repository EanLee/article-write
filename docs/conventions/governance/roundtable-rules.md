# 圓桌會議運作規則

> **建立日期**: 2026-02-03
> **最後更新**: 2026-06-13
> **版本**: v3.0（討論方式改為觀點驅動交互式，廢除固定輪次）
> **目的**: 建立跨角色討論與決策機制，透過多元視角打造更好的產品

---

## 🎯 會議定位

### 圓桌會議 vs 技術會議

| 面向 | 圓桌會議 | 技術會議 |
|------|---------|---------|
| 層次 | 戰略（What / Why） | 戰術（How / 實作細節） |
| 參與者 | 全體角色（五個角色） | 技術團隊成員 |
| 討論內容 | 產品方向、功能優先級、使用者價值、風險評估 | 實作方式、架構設計、程式細節 |
| 程式碼 | ❌ 不出現（除非特別需要上層決策的技術議題） | ✅ 正常出現 |
| 文件位置 | `docs/roundtable-discussions/` | `docs/tech-team/` |

### 戰略層面（✅ 圓桌討論）

- 產品定位與方向
- 功能優先級與 MVP 範圍
- 使用者價值與痛點
- 商業模式與推廣策略
- 跨團隊影響的重大決策
- 風險評估（影響產品方向層級）

### 戰術層面（❌ 技術會議處理）

- 具體技術實作方案
- 程式碼架構與資料結構
- API 設計、工具選型細節
- 開發步驟與任務分配

### 升級機制：技術會議 → 圓桌

**任何人**在技術實作過程中，若發現：
- 風險影響到產品方向或使用者體驗
- 需要多人共同決策而非技術團隊自行決定
- 實作結果與原本的戰略假設有落差

→ **主動發起圓桌會議**，無需等待上級指示。

**發起前提**：**必須先準備討論材料**（議題說明、背景、選項、影響評估），不得空手發起。

## 📋 發起流程

### 誰可以發起

**任何人**皆可發起圓桌會議，包含：
- 使用者（產品需求、功能想法）
- 技術團隊成員（發現實作風險影響策略）
- 任何角色成員

### 發起前必須準備

發起前**必須先備妥討論材料**，包含：

1. **議題說明**：要討論什麼、為什麼需要圓桌決策
2. **背景資訊**：相關歷史脈絡、現況說明
3. **討論選項**（若有）：可能的方向或方案
4. **影響評估**：對產品、使用者、時程的潛在影響

未準備材料者，請先整理後再發起。

## 📁 文件結構與命名

### 目錄結構

```
docs/roundtable-discussions/
├── README.md                                    ← 所有議題索引
├── .template/
│   ├── discussion.md                            ← 討論記錄模板
│   └── decision.md                              ← 決策記錄模板
├── topic-001-2026-02-03-product-launch/         ← 議題資料夾
│   ├── discussion.md                            ← 討論過程（完整記錄）
│   └── decision.md                              ← 決策結果（結論摘要）
├── topic-002-2026-02-06-progress-review/
│   ├── discussion.md
│   └── decision.md
└── ...
```

### 資料夾命名規則

```
topic-NNN-YYYY-MM-DD-簡短描述/
```

| 部分 | 說明 |
|------|------|
| `topic` | 固定前綴 |
| `NNN` | 三位數序號，從 001 起，全域唯一，反映時間順序 |
| `YYYY-MM-DD` | 發起日期 |
| `簡短描述` | 英文小寫，以 `-` 分隔，簡短描述議題 |

**範例**：
```
topic-006-2026-02-14-publish-mechanism/
topic-007-2026-02-14-frontmatter-date-fields/
```

同一天多個議題透過序號（NNN）區分前後順序。

### 兩份文件的分工

| 文件 | 內容 | 用途 |
|------|------|------|
| `discussion.md` | 完整討論過程，包含各角色論點、交叉回應、分歧點 | 了解決策脈絡 |
| `decision.md` | 決策結果摘要，包含行動項目、負責人 | 快速查看結論 |

## 💬 討論進行方式（核心規則）

**圓桌討論是觀點驅動的交互對話，不是輪次驅動的獨立陳述。**

### 基本流程

1. **主持人（Alex）開場**：點出議題、背景、待解決的問題
2. **任何角色提出觀點**後，其他角色針對**該觀點**自由回應：
   - ✅ **附議**：同意並可補充理由
   - 💡 **建議**：在該觀點基礎上提出修正或補強
   - ❌ **反對**：提出反向看法，必須附理由
   - 🤐 **不回應**：沒有意見就不需發言（不強制每個觀點人人表態）
3. **討論沿著觀點串自然延伸**：A 提出 → B 反對 → A 回應 B → C 補充……直到該觀點**取得共識或確認為分歧**
4. **不限定輪數**：共識自然收斂就結束；一個議題可能三句話達成共識，也可能來回十幾次
5. **主持人職責**：
   - 辨識「共識已達成」並當場宣告，記入共識點
   - 辨識「討論在原地打轉」，將該點標記為**分歧議題**
   - 控制討論不偏離議題範圍

### 共識與決策的關係（圓桌最重要的機制）

```
觀點提出 → 交互討論 → 自然收斂？
                        ├─ 是 → 記入「共識點」（不需表決）
                        └─ 否 → 標記「分歧議題」→ 進入正式決策程序
                                  （表決 / 主持人裁決 / 延後並列出待釐清項目）
```

- **能在討論中取得共識的，不需要表決**——表決是收斂失敗時的後備機制
- **只有無法收斂的分歧**才提交正式決策，這是圓桌會議存在的最重要目的
- 全程對話體記錄（`角色：「……」`），完整保留交鋒過程，包含被說服而改變立場的轉折

## 🔄 決策機制

**僅適用於討論中無法自然收斂的分歧議題**（能收斂的共識點不需走此程序）：

| 類型 | 條件 | 處理方式 |
|------|------|---------|
| 全體一致 | 五角色全部同意 | 直接執行 |
| 多數共識 | 三角色以上支持 | 記錄少數意見後執行 |
| 分歧但可行 | 正反接近 | 主持人裁決，或追加討論／小規模驗證 |
| 延後決策 | 資訊不足或風險過高 | 列出待釐清項目，排期再議 |

## ✅ Action Items 規範

### 什麼是合格的 Action Item

每個 Action Item 必須同時具備三個要素，缺一不可：

| 要素 | 說明 | 合格範例 | 不合格範例 |
|------|------|---------|-----------|
| **行動項目** | 具體要做的事 | 「建立 `MVP_STATUS.md`」 | 「整理一下進度」 |
| **負責人** | 有且只有一人 | Alex | 大家、全體、TBD |
| **完成條件** | 可驗證的結果 | 「文件建立完成，列出所有 MVP 功能的 Done 定義和當前狀態」 | 「做完」、「研究一下」 |

### 填寫位置

- **discussion.md 結尾**：`✅ Action Items 摘要`——會議結束前當場確認，確保每個人離開前都清楚自己要做什麼
- **decision.md**：`✅ Action Items`——正式追蹤，加上「狀態」欄，後續回顧時更新

### Action Items 狀態

| 狀態 | 說明 |
|------|------|
| `⏳ 待開始` | 尚未開始 |
| `🔄 進行中` | 已開始執行 |
| `✅ 完成` | 完成條件已達成 |
| `❌ 封存` | 因故不執行，須在備註說明原因 |

### 優先級定義

| 優先級 | 說明 |
|-------|------|
| `P0` | 本次決策的前提，不完成則決策無法生效 |
| `P1` | 本次 Sprint 必須完成 |
| `P2` | 下個 Sprint 完成 |
| `P3` | Backlog，排期再議 |

## ⚠️ 禁止事項

- ❌ 討論記錄出現程式碼（除非議題本身需要上層決策的技術選項）
- ❌ 任何角色缺席（五個角色必須全部出現）
- ❌ **各角色獨立陳述後直接總結**——沒有觀點之間的交互回應，不算討論
- ❌ **未經討論收斂就直接表決**——表決是分歧的後備機制，不是討論的替代品
- ❌ 空手發起（未準備討論材料）
- ❌ 在圓桌討論戰術細節（應移至技術會議）
- ❌ 決策後不更新 decision.md
- ❌ 會議結束時沒有 Action Items（沒有任何行動項目的會議，代表討論沒有產生共識，應繼續討論）
- ❌ Action Item 沒有負責人或沒有完成條件（這樣的 Action Item 無法被追蹤）
