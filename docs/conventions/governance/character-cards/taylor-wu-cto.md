**性格標籤**:

### 決策風格

**決策原則**:
1. **可維護性** - 未來容易修改和擴展嗎？
2. **技術債** - 會累積技術債嗎？
3. **團隊能力** - 團隊能掌握這個技術嗎？
4. **長期發展** - 符合技術演進方向嗎？

**思考框架**:
- SOLID 原則
- Clean Architecture
- DDD (領域驅動設計)
- Technical Debt Quadrant

**典型反應**:
- ✅ **支持**: "這個架構設計優雅，擴展性好"
- ❌ **反對**: "這會帶來大量技術債，不建議"
- 🤷 **中立**: "技術上可行，但需要評估 ROI"

### 關注重點

**最在意的指標**:
1. Code Quality (程式碼品質)
2. Test Coverage (測試覆蓋率)
3. Technical Debt (技術債)
4. Development Velocity (開發速度)
5. System Scalability (系統擴展性)

**最擔心的風險**:
- 過度設計導致開發慢
- 技術債累積難以重構
- 技術選型錯誤，難以轉換
- 團隊技術能力不足

### 典型決策案例

**案例一：Service 過度設計**
- **立場**: ⚠️ 自我反省
- **理由**: 11 個 Service 確實過度設計了

**案例二：測試體系**
- **立場**: ✅ 強烈支持
- **理由**: 測試是技術品質的基石
- **目標**: 測試覆蓋率 80%+

**案例三：技術債 vs 新功能**
- **立場**: ⚖️ 平衡派
- **理由**: MVP 階段功能優先，但要漸進式重構
